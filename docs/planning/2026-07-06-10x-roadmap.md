## 1. The core finding: value is captured but not compounding

Crux today is a strong *single-session* tutor: streaming chat, RAG over uploads,
deterministic MC grading, an editable topic profile, diagnostics, cost caps. The
audit found that almost everything needed for a *longitudinal* learning product
already exists in the data layer but is never exploited:

| Asset already captured | Where | What it is used for today | What it could power |
|---|---|---|---|
| Every graded answer (`gap_tested`, `question`, `correct`, timestamp) | `learning_events` | last-20 list, total count, demotion | per-gap accuracy, mastery trends, spaced repetition |
| Full quiz item records (options, selected/correct index, explanation) | `chat_messages.check_batch_json` | recap card re-render | item difficulty, distractor analysis, re-quiz pools |
| Profile carry-forward into a new session (`seed_mode=resume`) | `routes/sessions.py:102-134`, contract + JS client | nothing — UI always sends `fresh` | true cross-session learner memory |
| Retrieval relevance `score` | `pgvector_store.query_chunks` | computed, then dropped before the Citation contract | citation confidence UI, retrieval quality tuning |
| Per-user daily spend ledger | `daily_cost_ledger` | cap gating only | usage transparency dashboard |
| Evidence type (`declared`/`inferred`/`tested`) | validated at write in `profile_service` | discarded — profile stores flat string lists | per-concept confidence, smarter re-quiz priority |

The 10x thesis: **convert a session tool into a learning system with memory.**
A user who returns on day 7 should be met by what they got wrong on day 1.
Everything below is ordered by (leverage x readiness): backend-exists-UI-missing
first, new-engine work second, speculative content generation last.

## 4. Track P — Cost and latency (audit 2026-07-06)

Audit reality check: the whole pipeline runs on `gemini/gemini-3.1-flash-lite`
(`config.py:20`) — already the cheapest tier, so "use a cheaper model" is not
the lever. The levers are token volume per turn, billed loop iterations, and
time-to-first-token. All findings below carry file:line evidence from the
audit.

### P1 — Prompt-cache verification and exploitation (S-M, highest cost ROI)

Status: in PR (feat/roadmap-slice2) — AC1 instrumentation half shipped
(llm_call_log token columns, migration 0015, extract_usage); dogfood-day
measurement + cache decision = owed human gate; AC2 prefix guard test shipped;
AC3 stays documented-conditional.

Finding: zero caching configured anywhere (no `cache_control`, no LiteLLM
cache, no Gemini context cache — grep clean). CLAUDE.md's "structure matters
for cache reuse" is aspirational: `IMMUTABLE_RULES` (~1.3k tokens,
`prompts.py:17-117`) is a stable prefix but nothing measures or configures
caching, and every one of up to 8 loop iterations resends everything
(`tutor.py:74,299`).
- AC1: Instrument: log Gemini `cached_content_token_count` (implicit prefix
  cache) per call for one dogfood day; record hit rate in a short findings
  note. Decision recorded: implicit cache sufficient vs explicit context cache.
- AC2: Prompt assembly guarantees byte-identical stable prefix across turns
  and iterations: immutable rules first, all per-turn material (profile,
  retrieval flags, quiz state) after it; unit test asserts the first N chars
  of the system prompt are constant across two consecutive turn builds.
- AC3: If a model swap to Anthropic ever happens, `cache_control` breakpoints
  added at the immutable/dynamic boundary (documented as a conditional task,
  not built now).

### P2 — Token-volume reduction per turn (M)

Status: in PR (feat/roadmap-slice2) — AC1 (prune_superseded_excerpts), AC2
(truncate_message 6k chars head+tail), AC4 (token-budget tripwire), AC5 (cost
fallback) shipped; AC3 rolling summary deferred (composes with v2 draft-summary
item).

Finding: last-20-message window resent in full every iteration
(`chat.py:101-107`); each `retrieve_chunks` adds ~2.5k tokens (k=5 x 500-token
chunks) that get resent on every later iteration (`tutor.py:150-175`); no
truncation of long messages; `MAX_ITERS=8` with every iteration billed
(`tutor.py:340-356`).
- AC1: In-loop tool-result pruning: document_excerpt blocks from earlier
  iterations of the SAME turn are replaced by a one-line stub (id + doc name)
  once a newer retrieval supersedes them; unit test on the loop message
  assembly.
- AC2: Per-message truncation: individual history messages capped (e.g. 1.5k
  tokens with head+tail preservation) before assembly; boundary unit tests.
- AC3: Optional rolling summary of dropped-from-window turns appended to
  dynamic context (composes with the v2 "draft summary" backlog item); can
  ship separately.
- AC4: Regression guard: fixture-based token-count test asserting a standard
  3-turn conversation with one retrieval stays under an agreed budget;
  breaks loudly if assembly regresses.
- AC5: `cost_meter.MODEL_RATES` KeyError fragility fixed: unknown model falls
  back to `litellm.cost_per_token`/`completion_cost` instead of raising
  (`cost_meter.py:100-137`); test with an unregistered model id.

### P3 — Time-to-first-token (M)

Finding: ~9 sequential DB round trips in `_prepare_turn` (`chat.py:57-141`)
plus a `litellm.token_counter` over the full message list (`tutor.py:290`)
all run before the stream opens.
- AC1: Pre-stream DB work consolidated: independent reads (cost cap, session,
  history, profile, ingestion status, pending check, cooldown) fetched in at
  most 3 round trips (combined queries) or measurably parallelized; count
  asserted via a SQLAlchemy event-listener test that tallies statements on
  the prepare path.
- AC2: Pre-stream `token_counter` call removed or replaced with a cheap
  estimate (it exists only for soft-cap warning math); soft-cap warning tests
  still green.
- AC3: End-session summary LLM call moved off the request path (FastAPI
  BackgroundTasks — allowed: this is not the banned stale-session finalizer;
  it runs within the end-request lifecycle) OR explicitly kept synchronous
  with rationale recorded. End-session endpoint p50 measured before/after.
- AC4: Measurement, not vibes: a lightweight timing log (prepare_ms,
  first_token_ms) added behind debug flag; before/after numbers recorded in
  the PR description.

### P4 — Retrieval quality and index (S)

Finding: ivfflat lists=100 with per-session filter and default probes
(`0002_chunk_embeddings.py:51-55`); per-session row counts small; lexical
Porter-stem retrieval gate has false-negative modes (acronyms, digits,
paraphrase — `keyword_index.py:33-59`).
- AC1: Measure first: EXPLAIN ANALYZE on a realistic session corpus; if
  planner seq-scans (likely at small N), record that and leave index alone;
  only migrate to HNSW if ivfflat is actually used and recall-limited.
- AC2: Keyword gate false-negative softening: digit-bearing and 2-char tokens
  no longer dropped by `_TOKEN_RE` (acronyms like "DNA", "IPv4"); index
  rebuild on next ingest; unit tests for acronym/number queries flipping
  `retrieval_required`.
- AC3: Frontend stream render: `markdownStreamBuffer.splitSafePrefix` made
  incremental (scan from last-known-safe offset, not from zero) and deltas
  batched per animation frame; existing fence/math boundary tests green.

## 5. Track D — Smarter LLM decisions (audit 2026-07-06)

### D1 — Stop the agent re-teaching blind (M, highest quality ROI)

`check_question_service.py:266-280`) reaches the agent only on the immediate

- AC1: `quiz_cooldown_json` retains the missed-item list (gap, question

- AC2: Once R0.2 lands, dynamic context includes per-gap attempt counts and
  accuracy (from `learning_events`) for gaps in the current profile — capped
  token budget for this block (assembly test asserts the cap).
- AC3: LLM reliability spot-check per CLAUDE.md rules: eval script scenario
  where the tutor's next explanation references the missed concept; target
  85 percent or better on the existing eval harness pattern.

### D2 — Determinism and arbitration (S)

- AC1: Explicit `temperature` set on all `acompletion` calls (tutor,
  summary) — value decided in brainstorm (likely 0.2-0.4 tutor, 0.0 summary);

- AC2: Retrieval arbitration semantic fallback: when the lexical gate says
  OPTIONAL and a ready document exists, prompt guidance strengthened (or a
  cheap cosine check of query embedding vs session centroid) so the agent
  does not skip citing the user's own notes; measured via eval scenario, not

### S1 — document_excerpt delimiter escape (S, fix first)

Status: in PR (`feat/roadmap-slice1`) — AC1-AC2 implemented via a single
shared helper (`backend/agent/excerpt.py::wrap_chunk`, used by
`run_streaming` now that the non-streaming loop is deleted); embedded
`<document_excerpt>`/`</document_excerpt>` sequences are entity-escaped
before wrapping. AC3 (ingestion-time sanitization) decided against —
defense stays at the single wrap-point, not re-chunking.

Finding: retrieved chunk text is interpolated raw into
`<document_excerpt>` wrappers (`tutor.py:150-160,477-487`). A malicious
uploaded document containing the literal string `</document_excerpt>` closes
the tag early and plants instructions OUTSIDE the guarded region — defeats
the prompt-injection defense the wrapper exists for.
- AC1: Chunk text sanitized before wrapping (strip or entity-escape any
  `</?document_excerpt` sequence) in BOTH loop implementations (`run` and
  `run_streaming`) — single shared helper so they cannot drift.
- AC2: Unit test: chunk containing a forged closing tag arrives inside the
  wrapper, delimiter neutralized.
- AC3: Same sanitization applied at ingestion time is considered and
  explicitly decided against or adopted (defense in depth vs re-chunking
  cost) — decision recorded.

### S2 — check/complete rate-limit bypass (S)

Status: in PR (`feat/roadmap-slice1`) — AC1-AC3 implemented: follow-up turns
now count against the main 50/day cap (`rate_limit.check_and_increment` in
`sessions.py`); over-cap degrades gracefully via a new `followup_skipped` SSE
event + quiet FE notice, grading/recap unaffected; `check/answer`/`check/skip`
stay uncounted (existing tests unchanged).

Finding: every resolved quiz batch fires a full tutor streaming turn that
deliberately skips `rate_limit.check_and_increment`
(`sessions.py:423-435`); answer/skip endpoints also do not count. A
quiz-heavy user gets unbounded free turns against the 50/day message cap;
only the $3 cost hard-cap backstops.
- AC1: Follow-up turns counted — either increment the same daily counter or
  a separate `check_followup` counter with its own cap; decision in
  brainstorm (counting against the main cap changes UX copy).
- AC2: Cap-exceeded on the follow-up path degrades gracefully: batch still
  resolves and grades; only the free-text follow-up is skipped with a quiet
  notice — grading must never be blocked by the cap (test).
- AC3: Existing behavior tests for answer/skip (which correctly stay
  uncounted — they cost no LLM call) unchanged.
